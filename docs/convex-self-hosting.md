## How Convex Uses PostgreSQL

Convex connects to your PostgreSQL **server** (not a specific database) and manages its own database internally. The database name is derived from `INSTANCE_NAME` with hyphens converted to underscores.

Examples:

- `INSTANCE_NAME=convex-local` -> `convex_local` (local and Azure parity default)

### CONVEX_POSTGRES_URL format

```text
# Correct — no database name, just the server
postgresql://user:password@host:5432

# Wrong — do not specify a database name
postgresql://user:password@host:5432/convex
postgresql://user:password@host:5432/convex_local
```

For local Docker, the postgres init script (`docker/postgres/init/001-create-databases.sql`) pre-creates `convex_local` so Convex can connect immediately on first start. In Azure, Bicep also creates `convex_local` by setting `convexInstanceName=convex-local`.

## Environment Variables

### Container-level (passed into the Convex backend container)

| Variable | Description |
| --- | --- |
| `INSTANCE_NAME` | Unique name for this backend instance (e.g. `convex-local`, `convex-production`) |
| `INSTANCE_SECRET` | 64-char hex secret. **Generate:** `openssl rand -hex 32` |
| `POSTGRES_URL` | PostgreSQL server URL — **no database name** (see above) |
| `DO_NOT_REQUIRE_SSL` | `1` for local dev, `0` for production |
| `DISABLE_BEACON` | Set to `1` to opt out of telemetry (recommended for local dev) |

> These are named without the `CONVEX_` prefix inside the container. The `docker-compose.local.yml` maps `CONVEX_*` env vars from `.env` to the unprefixed names the container expects.

### CLI / developer tooling (used by `npx convex dev` and the dashboard)

| Variable | Description |
| --- | --- |
| `CONVEX_SELF_HOSTED_URL` | Public URL of the backend — port 3210. e.g. `http://127.0.0.1:3210` |
| `CONVEX_SELF_HOSTED_ADMIN_KEY` | Generated by running `./generate_admin_key.sh` inside the container |
| `CONVEX_CLOUD_URL` | Leave empty when using self-hosted |
| `CONVEX_DEPLOYMENT` | Leave empty when using self-hosted |

### API integration (used by the NestJS API to sync with Convex)

| Variable | Description |
| --- | --- |
| `CONVEX_SYNC_URL` | Internal URL for API → Convex communication (Docker: `http://convex-backend:3210`) |
| `CONVEX_SYNC_ADMIN_KEY` | Same admin key, used by the API to push functions |
| `CONVEX_BETTER_AUTH_URL` | Auth endpoint exposed to Convex for session validation |

### Frontend (Vite build args)

| Variable | Description |
| --- | --- |
| `VITE_CONVEX_URL` | Public URL the browser connects to (same as `CONVEX_SELF_HOSTED_URL` for local) |

## Generating the Admin Key

The admin key is **not set in advance** — it must be generated from the running container after first boot:

```bash
# Docker Compose
docker compose exec convex-backend ./generate_admin_key.sh

# Fly.io
fly ssh console --command "./generate_admin_key.sh"
```

Copy the output and set it in **both** places:

- `convex-backend/.env` → `CONVEX_SELF_HOSTED_ADMIN_KEY` (used by `npx convex dev/deploy`)
- `docker/.env` → `CONVEX_SYNC_ADMIN_KEY` and `CONVEX_SELF_HOSTED_ADMIN_KEY` (used by the API and CLI)

### Admin key is tied to the running container

The key is derived from `INSTANCE_SECRET` and the live container state. It becomes invalid when:

- The `convex-backend` container is recreated
- `INSTANCE_SECRET` changes
- The PostgreSQL data volume is wiped

**Any time the container is recreated, regenerate the key:**

```bash
docker exec retro-tool-local-convex-backend-1 ./generate_admin_key.sh
```

Then update both env files above and restart the API container:

```bash
docker compose -f docker/docker-compose.local.yml restart nest-api
```

Symptom of a stale key: `Operation query not permitted` error when running `npx convex dev`.

## Troubleshooting

### `Src Pkg storage key not found` (500 on `start_push`)

**Symptom:** `npx convex dev` fails with repeated 500 errors and the Convex container logs show:

```text
Hit an error while pushing: Src Pkg storage key not found?? ObjectKey("...")
```

**Cause:** Convex stores uploaded function packages on the **container's local filesystem**. PostgreSQL stores references to those packages. If the container is recreated (filesystem wiped) but the PostgreSQL volume persists, the database references objects that no longer exist on disk.

**Fix:**

```bash
# 1. Drop and recreate the Convex database to clear stale references
docker exec retro-tool-local-postgres-1 psql -U postgres -c "DROP DATABASE convex_local;"
docker exec retro-tool-local-postgres-1 psql -U postgres -c "CREATE DATABASE convex_local;"

# 2. Restart the Convex container
docker compose -f docker/docker-compose.local.yml restart convex-backend

# 3. Regenerate the admin key (restart invalidates the old one)
docker exec retro-tool-local-convex-backend-1 ./generate_admin_key.sh
```

Update `convex-backend/.env` (`CONVEX_SELF_HOSTED_ADMIN_KEY`) and `docker/.env` (`CONVEX_SYNC_ADMIN_KEY`, `CONVEX_SELF_HOSTED_ADMIN_KEY`) with the new key, then retry `npx convex dev`.

> To avoid this permanently, configure Convex to use an S3-compatible object store (e.g. MinIO) so storage survives container restarts. See the Convex self-hosting advanced docs.

## Local Docker Compose Setup

The `docker/docker-compose.local.yml` spins up:

| Service | Port | Purpose |
| --- | --- | --- |
| `postgres` | 5432 | Shared PostgreSQL for both the API (`app_local`) and Convex (`convex_local`) |
| `convex-backend` | 3210 (API), 3211 (HTTP actions) | Self-hosted Convex backend |
| `convex-dashboard` | 6791 | Web UI for browsing data and functions |
| `nest-api` | 8000 | NestJS REST API |
| `ui` | 3000 | React frontend |
| `redis` | 6379 | Cache / session store |

### Startup sequence

1. Copy `docker/.env.example` → `docker/.env` and fill in secrets
2. Start services: `docker compose -f docker/docker-compose.local.yml up -d`
3. Generate the admin key (see above) and add to `docker/.env`
4. Restart the API: `docker compose -f docker/docker-compose.local.yml restart nest-api`
5. Deploy Convex functions: `npx convex deploy` (uses `CONVEX_SELF_HOSTED_*` from `convex-backend/.env`)

## Production Setup

For production, Convex must run close to the database (same datacenter) for performance.

Recommended architecture:

- Convex backend as a Docker container (Azure Container Instance, Fly.io, etc.)
- Shared managed PostgreSQL (Azure Database for PostgreSQL, etc.)
- API reads/writes Convex via `CONVEX_SYNC_URL` using the admin key

### Production CONVEX_POSTGRES_URL

```text
# Azure PostgreSQL example — no database name
postgresql://pgadmin:PASSWORD@your-server.postgres.database.azure.com:5432?sslmode=require

# Set DO_NOT_REQUIRE_SSL=0 in production
```

## Port Reference

| Port | Purpose |
| --- | --- |
| 3210 | Convex API — used by clients, dashboard, and admin tools |
| 3211 | Convex HTTP actions — for webhooks and external HTTP endpoints |
| 6791 | Convex dashboard UI |

Inside Docker Compose, the API communicates with Convex on `http://convex-backend:3210` (internal Docker network), not `localhost`.
